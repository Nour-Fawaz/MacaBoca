\section{Project Decomposition and Scheduling}

We will use GitHub Projects as the single source of truth for documentation and
code (link to the GitHub project is \href{https://github.com/users/Nour-Fawaz/projects/8}{HERE}). The board (\textit{Maca Kanba})
contains all project issues, with a Kanban view for day-to-day work and a
table/roadmap view grouped by milestone. Every issue has at least one assigned owner to ensure it gets completed, though
there may be multiple collaborators if required. Two issue types are used:

\begin{enumerate}
    \item \textit{Documentation issues}: one per deliverable section, using the
    documents.md template (Document Name / Description / Due Date / Reviewed by).
    \item \textit{Code issues}: one per feature/module/task, using a separate code
    template.
\end{enumerate}

\medskip
\noindent\textbf{Milestones}

Milestones are grouped by graded deliverable date to help keep the team on track
for due dates. Peer-review milestones follow immediately after their
corresponding deliverable. For example, if M2 is SRS + Hazard Analysis, then
M2.1 is SRS Peer Review and all issues related to addressing feedback are
tracked there. Code-heavy sections (POC, Rev 0 module implementation, Rev 1) may get
their own milestones separate from any documentation due the same week, since
code issues require a separate lifecycle that relies more on testing and
thorough reviews.
