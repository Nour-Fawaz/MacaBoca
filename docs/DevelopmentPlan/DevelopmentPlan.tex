\section{Workflow Plan}

\subsection*{Git Usage}
The team will use Git and GitHub for version control and project management. After being
assigned individual tasks, team members are required to create an issue, and to create
and work on a new branch. All work will be completed on the branch and submitted for review through a pull request (PR).
All members are encouraged to review any open pull request, but 
at least one team member must review and approve the changes before the user
can merge their branch onto main. 

\subsubsection*{Naming Conventions}
The project will make use of following naming conventions:

\textit{Pull Requests/Commits}: \texttt{<type>(<scope>): <short description>}. The supported types are:
\begin{itemize}
    \item \texttt{feat}: Adding new functionality
    \item \texttt {fix}: Fixing a bug/error
    \item \texttt{docs}: Updating documentation
    \item \texttt{test}: Adding/updating tests
    \item \texttt{refactor}: Restructuring code, no external behavior change
    \item \texttt{chore}: Github maintenance, builds, dependencies
\end{itemize} The scope identifies the primary component or document affected by the change, such as \texttt{ui}, \texttt{backend}, \texttt{data}, or the name of a specific document. The scope can be omitted if no appropriate scope applies.

For example:
\begin{center}
\texttt{feat(ui): add activity selection screen}
\end{center}

\textit{Branches}: \texttt{<type>/<name>/<short-description>}, where \texttt{<type>} identifies the purpose of the branch, \texttt{<name>} identifies the contributor, and \texttt{<short-description>} briefly describes the work being completed. Descriptions should use lowercase words separated by hyphens.

For example:
\begin{center}
\texttt{feat/javayria/activity-selection-screen}
\end{center}

\subsubsection*{Handling Pull Requests}

When opening a pull request, the default template will be applied. It includes a description of the changes, added tests + test scenarios, linked issues, and a checklist. The checklist serves as a reminder 
for authors to review their work before submitting the pull request for review, but does not block it from being merged.
When merging pull requests, the `Squash and merge' option should be selected to help keep \textit{main}'s history clean and readable.

\subsection*{Issue Management}
All progress on the team will be tracked via Github Issues and a Kanban board. 
This includes every lecture and different type of meeting attended, as well as all
development tasks and deliverables. Template issues have been created for
each type of task/issue, and can be easily updated via configurable files in the repository;
currently including sections for dates, descriptions, and relevant notes. Each issue also
has a specific label to categorize it (e.g ``Lecture'' for Lecture Issues, and ``Bug''
all Development Bug Issues).
Each member will be responsible for updating their own issues with relevant pull requests (must be closed by updating the 'Linked Issues` section of the PR description),
and status changes as the task progresses. The coordinator will also regularly 
review the project board to ensure that all issues are on track.
\\\\
\underline{Issue Templates}:
\begin{enumerate}
    \item Lecture Issue: To track any relevant notes detailed in lecture.
    \item Supervisor Meeting Issue: To track all pre-meeting agenda items, questions, and notes with the supervisor and external teams.
    \item Team Meeting Issue: To track all pre-meeting agenda items, questions, and notes for general meetings.
    \item TA Meeting Issue: To track all pre-meeting agenda items, questions, and notes with the TA.
    \item Deliverable Issue: To track requirements and progress on all deliverable items.
    \item Blank Issue: To track any other important items.
\end{enumerate}

\subsection*{CI/CD}
To prevent any failures or issues from occurring, we'll be using Github Actions to implement
our main CI/CD pipelines. These workflows will then be triggered on every pull request
that opens or updates, and again on every merge to main. Each workflow will run 
the project's integration, contract or unit tests, and check for any formatting or
linting errors before allowing the changes to be merged. If any of these builds or runs
fail, the team member who opened the pull request must go back and fix the issue before 
merging. Another workflow will also be added to compile our LaTeX documentation whenever a
\texttt{.tex} file is changed, ensuring that every document still generates a PDF without
any errors. The compiled PDFs will also be uploaded as artifacts so whoever is reviewing
the pull request can actually verify the final formatted output before approving.
Once every check has passed, a final team member must stamp their approval in order to
finally merge the changes into main.
\\\\
\underline{Workflow Summary}:
\begin{enumerate}
    \item Brainstorm and discuss all tasks as a team.
    \item Individual task is assigned to a team member, who creates an issue on the kanban board to track.
    \item Team member creates a new branch from latest main, to work on their task. They must ensure that they're frequently pruning their branch to the latest main.
    \item Any progress or significant changes should be updated on the kanban issue board.
    \item Team member regularly commits their changes, with descriptive/clear commit messages that follow the outlined naming conventions.
    \item Once the task is complete, the team member submits a pull request, and assigns a reviewer. The pull request description should include be complete, with all template fields filled out and checklists up to date.
    \item The reviewer checks the PR, following any testing or tophatting instructions provided, and leaves comments if it needs any changes. If not, they approve the PR with a smiley face.
    \item Once the PR is approved, the team member double checks their work and merges their branch into main.
    \item Team member closes the issue on the kanban board if it was not done by an accompanying PR.
\end{enumerate}

\section{Proof of Concept Demonstration Plan}
A high-level overview of our proof of concept demonstration:

\begin{enumerate}
  \item A patient will have previously recorded a bilingual assessment session on the
  TeleHealth platform.
  \item The clinician will log in and select the same patient profile and
  language assessment session from the patient's history.
  \item The SAFA interface retrieves a transcript of the recording, divided into
  time-coded chunks with clinically meaningful markers (e.g., language switches,
  utterances, and assessment tasks).
  \item The clinician reviews and annotates the transcript, verifies the markers, and
  labels key details about the speaker and their performance to support their
  assessment of the patient's language abilities.
\end{enumerate}

The high-level plan above does not fully address the major risks that could arise
during the project, but we have identified ways to address these issues.

\begin{itemize}
  \item By failing to properly \textbf{integrate SAFA into the TeleHealth platform},
  clinicians will have to leave the web platform and transfer files manually
  to SAFA, defeating one of the project's main purposes. The main concern
  is that SAFA was built as a local, standalone tool, whereas TeleHealth
  exists as a prototype web-based platform with its own architecture and design.
    \begin{itemize}
      \item To address this, the POC will demonstrate an end-to-end workflow in which
      clinicians access a patient's recorded assessment session within the TeleHealth
      platform and use SAFA's core modules. The usability and performance of each
      module, including chunk editing, video playback, and annotation markers, will
      be compared with its performance in the standalone SAFA tool to verify successful
      integration.
    \end{itemize}

  \item Another large risk is failing to \textbf{keep the video and transcript synchronized in
  the browser}. Clinicians might make edits to the wrong sections of the transcript
  and become confused by the timing. SAFA depends on the video and transcript staying
  aligned so clinicians can make precise edits. Streaming video over the web can also
  add delay and buffering that may not occur when running SAFA locally, which could contribute
  to synchronization issues. This will require extending TeleHealth's Media Processing
  module to stream video and seek to specific timestamps, rather than loading the full
  file at once.
  \begin{itemize}
    \item To address this, the POC will play a full-length recorded session
    (at least 10 minutes) and repeatedly jump between sections from the start, middle,
    and end of the video. We will check that the highlighted chunk matches what is
    being said and measure the gap between the video's timestamp and the transcript's
    timestamp. As a tentative target, we can aim to keep this gap under half a second
    with no noticeable drift throughout the demonstration.
  \end{itemize}

  \item The system may also struggle to properly \textbf{categorize and pre-annotate
  important parts of the transcript}. If this happens, clinicians may still need to
  manually search through entire recordings for key moments and markers, reducing the
  time savings that the transcription and annotation modules are intended to provide.
  \begin{itemize}
    \item To address this, the POC will compare the system's automatically generated
    markers and tags against a manually reviewed sample of the recording. We will
    measure how accurately the system identifies speaker turns, language changes,
    assessment tasks, and significant moments, as well as how much time these markers
    save during clinician annotation.
  \end{itemize}

  \item Finally, one of the largest risks is failing to \textbf{protect patient data}.
  Unauthorized users may gain access to assessment videos, transcripts, and annotations.
  Since these files will live in the clinician's TeleHealth account, unauthorized access
  could result in a serious security failure and expose sensitive information about
  children.
  \begin{itemize}
    \item To address this, the POC will use TeleHealth's existing authentication to
    show that a clinician can only access recordings and annotations for their own
    patients. We will also verify that patient data is encrypted during transmission
    and stored securely. This will be demonstrated by logging in as a second clinician
    account and confirming that it cannot view or edit the first clinician's data,
    including through direct links or API requests.
  \end{itemize}
\end{itemize}

\noindent If the team is unable to make progress on the risks above, it could lead to
minor or major consequences for the project. Addressing these risks early will help the
team confirm that the project is feasible and define clear metrics for
success.

For written deliverables, the team member may ask the LLM whether their writing covers the “Exceeds” criteria in the corresponding rubric posted on avenue.

\subsection{Verification of LLM Output} \label{sec:Verf_LLM_Output}
In order to verify the output of the LLM, every line of code and writing must first be reviewed and completely understood by the individual generating the output of the LLM. 
For example, if the team member uses an LLM to generate code they must be able to explain to another member what the code is doing. 
Additionally, if they generate writing, they must understand what the writing means. 
If the team member is unable to do so, they must revise their section such that they are confident in their work and can clarify what is being done. 
This goes in hand with using an LLM as a checking tool.

Next, each team member’s section pertaining to all project tasks, including those generated or checked with an LLM, will be reviewed by another group member.
For written sections, the reviewing member will check whether the writing is clear, concise and understandable. 
As for code, the member will determine if it is clean, readable, maintainable, and if it follows the code standard outlined in \hyperref[sec:Code_Standard]{Section 12}.

\subsection*{Javayria}
If there's one thing I took away from my co-op, it's that structure and planning 
before starting a project is extremely necessary. We are all software engineers with our own 
ways of thinking and working, and while individuality is great, there needs to be some pre-agreed upon, 
formalized set of rules and methodologies for the team to succeed. Having a plan allows the team to focus on
 what's important rather than getting lost in fine-grained details. It also sets a standard, where everyone is aware of the level 
 of work quality expected of them beforehand, so they can keep that in mind while working. 
 Is it difficult to confront a team member who isn't contributing to the level expected of them? Yes, it is. 
 However, that's much less likely to happen if the conversation happens at the very beginning, since it helps the team find common
ground and ensures everyone goes into the project with the same mindset. I feel confident that my team members and I will benefit from
having this plan in place as the project grows more and more complex.

One of the biggest advantages of CI/CD is that it helps catch mistakes and issues with the code before it goes to production (or in this case, the main branch). 
Running and troubleshooting builds manually is an extremely frustrating process (as any software engineer can tell you!), so having a workflow 
run a linter or unit tests against new changes before they're ready to be merged is a great first step for verification. One of the 
major drawbacks, though, is the amount of time it takes to both run and troubleshoot CI/CD pipelines (here, we mean in the context of GitHub). 
It's very easy to find yourself waiting on a 30-minute build pipeline, only for it to fail midway and need to be run again. 
This can slow down the coding process and cause PRs to take multiple days to be reviewed and merged. I expect that we will need to tweak/update the workflows throughout
the term as we notice certain parts taking too long or repeatedly failing.

\section*{Appendix --- Team Charter}

\subsection*{External Goals}

For this capstone project, our team's external goals are to achieve an A+ first and foremost,
but to also have a finished product that actually demonstrates what we've learned about
healthcare in a speech-language pathology setting, and also how technology can actually 
reduce barriers that many in the field face, from both clinicians and patients. We hope
to have a product that future employers can utilize, and also showcase on our resumes
to show off our skillset as engineers.

\subsection*{Attendance}

\subsubsection*{Expectations}

All team members are expected to arrive on time to pre-agreed meetings and remain for the entirety of the scheduled time slot. 
Team members are expected to attend all meetings unless they notify the group in advance that they are unable to attend. 
Notice should be provided at least one day before the meeting whenever possible. 
If a team member is unable to attend a meeting, they are responsible for reviewing the meeting notes, 
communicating with the team as necessary, and completing their assigned work before the next meeting. Missing more than three meetings will result in a meeting with the rest of the team to discuss next steps. Lastly, team members are expected to arrive prepared, with any technical or administrative tasks assigned prior to the meeting completed.


\subsubsection*{Acceptable Excuse}

Acceptable reasons for missing a meeting include unexpected emergencies, 
health-related circumstances, and anticipated absences. Emergency circumstances 
will be addressed with consideration for the situation. 
Team members should communicate any health-related absence or anticipated impact on 
their availability, such that the team can adjust the workload. Anticipated absences 
should be communicated before the meeting is scheduled, or as soon as the member becomes aware of the conflict.

\subsubsection*{In Case of Emergency}

If an emergency does occur, the member does not need to alert the rest of the team. 
They can do so afterwards when reasonably able. The team will bring flowers and do 
their best to console the team members. In the case that the emergency coincided with a 
deadline, the affected team member may make up their contribution through future tasks.

\subsection*{Accountability and Teamwork}

\subsubsection*{Quality} 

Team members are expected to spend 20-30 minutes reviewing relevant documents before each meeting, or enough to contribute meaningfully and raise questions or notes as needed. Before meetings with the supervisor, all members must be fully aware of the project's status and prepared to both ask and answer questions.

For deliverables, each member is responsible for completing their assigned section to the best of their ability: original content, free of spelling and grammar errors, and going beyond the bare minimum. If a section is entirely AI-generated, the author must be able to explain the writing/code and prove to have a deep understanding of the work they put out. All team members are responsible for properly testing their code with the appropriate endpoints to ensure any existing functionality is not broken. Each section should be checked against the Avenue rubric to confirm all requirements are met, and reviewed by a designated team member before submission.

All deliverables must be finalized two days before the official deadline to allow time for review. Any issues found afterward are to be fixed by the original author. Final submission occurs by 7:00 pm on the due date to allow time for technical issues.

\subsubsection*{Attitude} \label{sec:Attitude}
\textbf{Code of Conduct} \\ 
The following code of conduct was developed by the team and outlines what is expected in terms of attitude, behaviour, cooperation, and contribution from each team member.
\begin{itemize}
    \item \textbf{Communication}: All team members are expected to communicate with one another in a kind and respectful manner. They should approach all conversations with an open-mind and be willing to take constructive feedback when needed. Additionally, all team members are expected to respond to group messages within approximately 1-2 hours of being directed at them.
    \item \textbf{Positive Attitude}: All team members are expected to approach tasks with a positive attitude and outlook to maintain team morale and encourage one another.
    \item \textbf{Collaboration}: All team members are expected to communicate their thoughts and ideas, participate thoroughly in group meetings by providing feedback and constructive criticism, and cooperate efficiently and effectively with other members.
    \item \textbf{Task Completion}: All team members are expected to have their tasks completed by the agreed upon deadlines. Additionally, group members must remain proactive and help other group members who are struggling with their tasks.
    \item \textbf{Dedication to Quality}: All group members are expected to complete their tasks with the utmost quality and to the best of their abilities.
\end{itemize}
\textbf{Conflict Resolution Plan} \\ 
When experiencing conflict, the following guide will be used:
\begin{enumerate}
    \item The team will hold a group discussion allowing each team member to share their perspective in order to pinpoint the root of the problem
    \item The team will brainstorm potential solutions to the problem by finding common ground through shared goals and interests.
    \item The team will develop a solution plan that all opposing parties are satisfied with.
    \item The team will begin implementing the plan and monitoring its progress. If the solution yields no results, the team may repeat the process until a proper solution is reached.
\end{enumerate}

Members with exceptional performance will be rewarded by having their hard work and dedication acknowledged by the team. 
This may also be rewarded by taking on more leadership roles, provided they are open to doing so. 
Additionally, other members are free to reward them with snacks. \\

\noindent \textbf{Target Metrics and Consequences} \\
Members who are performing below expectations will be confronted by the team in a kind and supportive manner. 
They will be asked about the cause of their reduced performance, and the team will work with them to address the issue constructively. 
However, if the member remains unresponsive the team will follow the conflict resolution plan outlined in the \hyperref[sec:Attitude]{Attitude} section. If all else fails, the issue will be raised with the TA and, if necessary, the course instructor. 
\begin{itemize}
    \item \textbf{Attendance}: Team members are expected to attend all in-person group meetings. If they are unable to attend in person, they must join online unless they have an emergency. If a group member misses the target metrics outlined above more than twice, the team will first meet with them to discuss the behaviour. 
If the member’s behaviour persists and deadlines continue to be missed, the issue will be raised with the TA and, possibly, the course instructor. 
This also applies if a group member consistently fails to contribute fairly to the project, which can be analyzed via their completed issues and number of commits.

If a group member consistently reaches the target metrics early, they will be given the choice of the next meeting's location, or the ability to set restrictions on where it will be held.

\subsubsection*{Decision Making} 

All group decisions will be made by reaching a consensus, rather than a vote. This ensures that all group members are satisfied with the outcome of the decision. \\

\noindent The team will follow the process below to handle disagreements:
\begin{enumerate}
    \item Each member will be given a turn to share their opinion and thoughts on the matter, while maintaining a positive attitude as outlined in the \hyperref[sec:Attitude]{Attitude} section. 
    \item After hearing everyone’s perspective, the team will hold a short, project-focused discussion to work toward an agreed-upon consensus. Relevant technical documentation may be referenced during this discussion to ensure that project goals continue to be met.
    \item If aconsensus is still not reached, a neutral third party, which can include an uninvolved team member or an individual onboard with the project, may facilitate the discussion or offer their perspective to help the group reach an agreement.
\end{enumerate}
