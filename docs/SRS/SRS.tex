\subsection{Characteristics of Intended Reader} \label{sec_IntendedReader}

\plt{This section summarizes the skills and knowledge of the readers of the
  SRS.  It does NOT have the same purpose as the ``User Characteristics''
  section (Section~\ref{SecUserCharacteristics}).  The intended readers are the
  people that will read, review and maintain the SRS.  They are the people that
  will conceivably design the software that is intended to meet the
  requirements.  The user, on the other hand, is the person that uses the
  software that is built.  They may never read this SRS document.  Of course,
  the same person could be a ``user'' and an ``intended reader.''}

\plt{The intended reader characteristics should be written as unambiguously and
  as specifically as possible.  Rather than say, the user should have an
  understanding of physics, say what kind of physics and at what level.  For
  instance, is high school physics adequate, or should the reader have had a
  graduate course on advanced quantum mechanics?}

\subsection{System Constraints}

\begin{itemize}
\item \textbf{Integration with TeLaC:} The system must be integrated into the
  existing TeLaC telehealth platform and accessed through the clinician dashboard,
  rather than as a separate standalone application. \textit{Rationale:} Clinician
  workflows require more than just the analysis of a single assessment. In order to 
  connect their work, they have should a platform that is able to help collect, review,
  transcribe, and annotate assessments across multiple patients and time.

\item \textbf{Web-based deployment:} The system must be a web application, deployed
  to a server and accessible through the web. The SAFA module, which is currently a
  Python desktop application, must be adapted to run within this web-based environment.
  \textit{Rationale:} TeLaC is a web-based platform, so SAFA must also run in the
  browser to work within it. This also means clinicians can access the system from
  any device with a web browser, without needing to install or maintain a separate
  desktop application.

\item \textbf{Assessment transcriptions:} For automatic transcription within
  assessments, the system must use
  the pre-trained Whisper model under OpenAI, no other models will be trained and used for
  transcription. \textit{Rationale:} The research team's existing workflow uses 
  Whisper to generate the transcripts reviewed in SAFA, and training a new model 
  is outside the project scope.

\item \textbf{Health and privacy regulations:} The system must comply with all
  health and privacy regulations in the country that it's used in (e.g., HIPAA
  in the United States). \textit{Rationale:} The system stores
  recordings and records of children, which are protected health information.
  Leakage of such private information could have serious consequences for these
  families, as well as legal consequences for the research team.
\end{itemize}

\section{Use Cases}
\plt{Use cases are a way to describe the interactions between users and the system.
  They are typically written in natural language and describe the steps that a
  user takes to achieve a specific goal.  Use cases can be used to identify
  functional requirements and to create test cases.}  
\plt{Typically 8-15 substantial use cases.}

\refstepcounter{ucnum} \label{UC_LogIn}
\subsection{\ucref{UC_LogIn}: Log In}

\textbf{Primary Actor}

Clinician, Researcher

\textbf{Preconditions}
\begin{itemize}
\item User has an existing TeleHealth account with a clinician or researcher
  role.
\item User is on the platform's login page.
\end{itemize}

\textbf{Main Success Scenario}
\begin{enumerate}
\item User enters their email and password.
\item The system verifies the credentials and authenticates the user.
\item The system identifies the user's role.
\item Using the user's role, the system redirects the user to the correct home page view.
\end{enumerate}

\textbf{Alternative Flows}
\begin{itemize}
\item 1a. The user has forgotten their password: the user selects ``Forgot
  password'' and follows the reset process.
\item 2a. When the credentials are incorrect, the system shows an error message and
  prompts the user to try again.
\item 2b. The user has too many failed attempts, the system temporarily locks
  the account until the user resets it.
\end{itemize}

\textbf{Postconditions}
\begin{itemize}
\item The user is logged in, and can only access the data allowed by their role.
\end{itemize}

\refstepcounter{ucnum} \label{UC_LogOut}
\subsection{\ucref{UC_LogOut}: Log Out}

\textbf{Primary Actor}

Clinician, Researcher

\textbf{Preconditions}
\begin{itemize}
\item The user is logged in (\ucref{UC_LogIn}).
\end{itemize}

\textbf{Main Success Scenario}
\begin{enumerate}
\item The user selects the Log Out option.
\item The system asks the user to save any edits and annotations.
\item The system redirects the user back to the login page.
\end{enumerate}

\textbf{Alternative Flows}
\begin{itemize}
\item 1a. The user is inactive for over 20 minutes, so the system 
  automatically logs them out after saving their work, and shows a 
  message explaining why.
\end{itemize}

\textbf{Postconditions}
\begin{itemize}
\item User cannot access any data or their account again
  without logging back in.
\end{itemize}

\refstepcounter{ucnum} \label{UC_ViewPatientList}
\subsection{\ucref{UC_ViewPatientList}: View Patient List}

\textbf{Primary Actor}

Clinician

\textbf{Preconditions}
\begin{itemize}
\item The clinician is logged in (\ucref{UC_LogIn}).
\end{itemize}

\textbf{Main Success Scenario}
\begin{enumerate}
\item The clinician opens the patients tab to view their list of patients.
\item The system retrieves the patients assigned to the clinician.
\item The system displays the list of patients with information, such as their name,
  age, and the date and status of their most recent assessment.
\item The clinician searches, sorts, or filters the list to find a patient.
\item The clinician selects a patient to view their profile.
\end{enumerate}

\textbf{Alternative Flows}
\begin{itemize}
\item 2a. If the clinician has no assigned patients, the system shows an empty list
  with a message explaining that no patients are assigned yet.
\item 4a. If no patients match the search or filter criteria, the system shows a ``no
  results'' message and the clinician can clear the search.
\end{itemize}

\textbf{Postconditions}
\begin{itemize}
\item Only the clinician can see the patients assigned to them and their information.
\item On select, only the selected patients profile is displayed.
\end{itemize}

\refstepcounter{ucnum} \label{UC_SelectAssessment}
\subsection{\ucref{UC_SelectAssessment}: Select a Submitted Assessment from a Patient}

\textbf{Primary Actor}

Clinician

\textbf{Preconditions}
\begin{itemize}
\item The clinician is logged in and has selected a patient
  (\ucref{UC_ViewPatientList}).
\item The patient has submitted at least one assessment.
\end{itemize}

\textbf{Main Success Scenario}
\begin{enumerate}
\item The system displays all the patient's submitted assessments, each with its
  date, assessment type, and review status, which are also filterable.
\item Clinician then selects an assessment.
\item The system displays the assessment's details; including its recordings, metadata,
  and report if one has been previously submitted.
\item The system provides the option to analyze the assessment, if not previously done before.
\end{enumerate}

\textbf{Alternative Flows}
\begin{itemize}
\item 1a. If the patient has not submitted any assessment, the system shows a
  message saying no assessments are available.
\item 3a. The recording is missing or corrupted, so the system shows an error and
  flags the assessment to be followed up on.
\end{itemize}

\textbf{Postconditions}
\begin{itemize}
\item The selected assessment is ready to be analyzed and annotated with SAFA.
\end{itemize}

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_AssessmentHistory}:] The system
  shall display to the clinician all previous assessments for a selected patient in
  chronological order.

  \textit{Rationale:} Clinicians must be able to track a patient's progress across multiple
  assessments over time.

  \textit{Fit Criterion:} For a selected patient, all completed assessments are
  listed, ordered from most recent to oldest by assessment date, and able to be
  searched and filtered through.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_AssessmentOverview}:] The system
  shall display an overview of every assessment's results, including automatically 
  flagged items and the patients overall results, without requiring a transcript.

  \textit{Rationale:} When reviewing many assessments, clinicians need a quick
  summary without having to perform any in-depth transcription and annotation.

  \textit{Fit Criterion:} The overview for each completed assessment should show a score and
  status for every question, like ``pass'' or ``flagged'', and can be viewed before the assessment goes into review
  via using the SAFA tool.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_DetectInterference}:] The system
  shall detect potential interference in video assessments and report it to the
  clinician.

  \textit{Rationale:} During assessment, outside help or disruptions (e.g.,
  parents giving hints to the child) can heavily impact results and potentially make them invalid.

  \textit{Fit Criterion:} Each question with detected interference is visibly
  marked in the assessment overview.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_QuestionTimestamp}:] The system
  shall allow the clinician to navigate to the point in the video assessment where
  a selected question was asked.

  \textit{Rationale:} When searching for a specific moment or question asked in an assessment,
  given a transcription, clinicians should not have to search through a full recording
  to review that moment.

  \textit{Fit Criterion:} Selecting a question or specific moment in a conversation starts video playback
  to that specific point in the assessment playback.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_ManualEvaluation}:] The system
  shall allow the clinician to always require manual evaluation of questions that cannot be
  automatically evaluated, using video playback of the recorded answer.

  \textit{Rationale:} Some responses, such as open-ended answers, cannot be scored
  automatically and require clinical judgement. Other times, the system simply
  might not be able to automatically score a question, so the clinician must
  manually evaluate it.

  \textit{Fit Criterion:} For each question without an automatic score, the clinician
  can play the recorded answer and assess it, which is then saved to the
  assessment results.

\plt{List your nonfunctional requirements.  You may consider using a fit
  criterion to make them verifiable.}

\plt{The goal is for the nonfunctional requirements to be unambiguous, abstract
  and verifiable.  This isn't easy to show succinctly, so a good strategy may be
to give a ``high level'' view of the requirement, but allow for the details to
be covered in the Verification and Validation document.}

\plt{An absolute requirement on a quality of the system is rarely needed.  For
  instance, an accuracy of 0.0101 \% is likely fine, even if the requirement is
  for 0.01 \% accuracy.  Therefore, the emphasis will often be more on
  describing now well the quality is achieved, through experimentation, and
  possibly theory, rather than meeting some bar that was defined a priori.}

\plt{You do not need an entry for correctness in your NFRs.  The purpose of the
  SRS is to record the requirements that need to be satisfied for correctness.
  Any statement of correctness would just be redundant. Rather than discuss
  correctness, you can characterize how far away from the correct (true)
  solution you are allowed to be.  This is discussed under accuracy.}

\noindent \begin{itemize}

\item[NFR\refstepcounter{nfrnum}\thenfrnum \label{NFR_Accuracy}:]
  \textbf{Accuracy} \plt{Characterize the accuracy by giving the context/use for
    the software.  Maybe something like, ``The accuracy of the computed
    solutions should meet the level needed for $<$engineering or scientific
    application$>$.  The level of accuracy achieved by \progname{} shall be
    described following the procedure given in Section~X of the Verification and
    Validation Plan.''  If you do this provide a link to the VnV plan.}

\item[NFR\refstepcounter{nfrnum}\thenfrnum \label{NFR_Usability}:] \textbf{Usability}
  \plt{Characterize the usability by giving the context/use for the software.
    You should likely reference the user characteristics section.  The level of
    usability achieved by the software shall be described following the
    procedure given in Section~X of the Verification and Validation Plan.  Include a link to the VnV plan.}

\item[NFR\refstepcounter{nfrnum}\thenfrnum \label{NFR_Maintainability}:]
  \textbf{Maintainability} \plt{The effort required to make any of the likely
    changes listed for \progname{} should be less than FRACTION of the original
    development time.  FRACTION is then a symbolic constant that can be defined
    at the end of the report.}

\item[NFR\refstepcounter{nfrnum}\thenfrnum \label{NFR_Portability}:]
  \textbf{Portability} \plt{This NFR is easier to write than the others.  The
    systems that \progname{} should run on should be listed here.  When possible
    the specific versions of the potential operating environments should be
    given.  To make the NFR verifiable a statement could be made that the tests
    from a given section of the VnV plan can be successfully run on all of the
    possible operating environments.}

\item Other NFRs that might be discussed include verifiability,
  understandability, reusability, performance, reliability and availability, security, and accessibility.  You may have to add other NFRs.

\end{itemize}
