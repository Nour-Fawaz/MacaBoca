\section{General Information} \label{sec:General_Information}
This section provides a brief overview of the software being produced and its objectives, how it will be tested and its relevant documentation.

\subsection{Summary}
The software being tested is TeLaC, a platform for remote speech and language assessment of Mandarin-English bilingual children. It addresses the usability and workflow challenges speech-language pathologists (SLPs) face when conducting remote assessments of bilingual pediatric patients. 
It does this by integrating the SAFA annotation tool into one platform, auto-generating transcripts, providing a hub for patient records and assessment results, and generating assessment reports. The goal is to help clinicians conduct assessments more efficiently and consistently while supporting ongoing monitoring of a child’s speech development, all in one centralized system.

The objective of this VnV plan is to build confidence that TeLaC is usable, accurate, and trustworthy enough to support clinical decisions. 
TeLaC assists clinicians and does not replace their judgment (\srssr*{3}). 
The requirements being verified are defined in the \SRSLink, and the risks that determine test priority are identified in the \HALink. 
The system has three main components described below.

\subsubsection{User Interface}
The user interface must be intuitive and easy to navigate for clinicians with limited technical fluency (\srssr*{8}, \srsnfr*{1}, \srsnfr*{2}). 
SLPs use it for the entire workflow, from selecting a patient to downloading a report (\srsfr*{5}, \srsfr*{9}). 
A confusing interface slows them down and risks mistakes, so the plan verifies the following:
\begin{itemize}
  \item Clinicians can complete core tasks, such as assigning a speaker role, viewing results, and adding a patient, without training (\srsnfr*{1})
  \item Clinicians can move between workflow stages without losing saved work (\srsfr*{5}, \srsnfr*{3})
  \item Clinicians can always tell which content is automatically generated and which they have verified (\srsfr*{14}).
\end{itemize}

\subsubsection{Audio Analysis Tool (SAFA)}
SAFA auto-generates transcripts of the assessment recordings and identifies speakers (\srsfr*{1}, \srsfr*{4}). 
Clinicians then verify and correct these outputs (\srsfr*{2}, \srsfr*{6}). 
Transcript accuracy is critical considering errors in code-mixed Mandarin-English speech, can lead to wrong conclusions about a child’s abilities (\SRSLink{} Section 9.4). 
The system is therefore tested to ensure that:
\begin{itemize}
  \item Transcripts are generated reliably for supported videos (\srsfr*{1}, \srsnfr*{17})
  \item The transcript stays synchronized with the recording during playback (\srsfr*{20}, \srsfr*{21}, \srsnfr*{13})
  \item Clinician edits and annotations are saved and persist across sessions (\srsfr*{2}, \srsfr*{19}, \srsnfr*{18})
\end{itemize}

\subsubsection{Report Generation}
Report generation compiles a patient’s results, the clinician’s edits, and notes into a report that the SLP can review and edit before downloading (\srsfr*{7}, \srssr*{6}). 
Because the report becomes part of the clinical record and may be relied on by families, schools, and other professionals, its correctness is crucial. 
The system is therefore tested to ensure that:
\begin{itemize}
  \item Every change a clinician makes must appear in the report, otherwise the automatically generated content remains as is (\srsfr*{7})
  \item Edits to results are reflected correctly and instantly (\srsfr*{8}, \srsnfr*{4})
  \item Exports and reports are only accessible to the assigned clinician (\srsnfr*{5}, \SRSLink{} Section 7.5)
\end{itemize}


\subsection{Objectives}

This VnV plan aims to evaluate whether TeLaC meets its key goals for transcript and report correctness, patient data security, and usability of the integrated workflow. Priorities come from the risks identified in the \HALink{}. The following subsections define each objective in the context of this project.

\subsubsection{Ensure Accuracy of Transcripts and Report Generation}
It is important to make sure clinicians can trust the information TeLaC provides to them. Since the report relies on the generated transcripts, the correctness of both aspects is an objective of the project. The system should:
\begin{itemize}
  \item \textbf{Generate transcripts reliably:} The supported assessment videos should produce a transcript at a rate of at least GENERATE\_SUCCESS (\srsfr*{1}, \srsnfr*{17}).
  \item \textbf{Distinguish speakers:} Each utterance in a transcript should be labelled with the correct speaker (\srsfr*{4}).
  \item \textbf{Reflect clinician changes in reports:} Every edit and annotation a clinician saves should also appear in the patient record and the generated report (\srsfr*{7}, \srsfr*{19}).
  \item \textbf{Preserve clinician work:} Saved edits should persist across sessions, and data should be backed up regularly and restorable without loss (\srsnfr*{9}, \srsnfr*{18}).
\end{itemize}

\subsubsection{Ensure Security and Privacy of Patient Data}
TeLaC stores recordings, transcripts, and health information about children. A breach would harm patients and violate HIPAA, so protecting this data is a key objective of the project. The system should:
\begin{itemize}
  \item \textbf{Restrict access:} Clinicians should only be able to access the patients assigned to them, including through URLs and the API (\srsnfr*{5}).
  \item \textbf{Protect idle sessions:} Sessions should end after IDLE\_TIMEOUT minutes of inactivity, and credentials should be required before any patient data is shown again (\srsnfr*{6}).
  \item \textbf{Encrypt patient data:} Recordings and transcripts should be encrypted in transit and in storage, including when sent to third-party transcription services (\srsnfr*{7}).
  \item \textbf{Log access:} Every view, change, download, and export of patient data should be recorded in an audit log that clinicians cannot edit (\srsnfr*{8}).
  \item \textbf{Meet compliance requirements:} The HIPAA technical safeguards should be satisfied, and third-party services handling patient data should be covered by a Business Associate Agreement (\srsnfr*{15}).
\end{itemize}

\subsubsection{Demonstrate Usability of the Integrated Workflow}
TeLaC's main value is combining SAFA and the clinician dashboard into one workflow. If the workflow is confusing, clinicians lose time and risk making mistakes, so usability is the final objective of the project. The system should:
\begin{itemize}
  \item \textbf{Provide a user-friendly interface:} The interface should be clear and consistent, with readable text, labelled controls, and a layout that clinicians with limited technical fluency can navigate easily (\srssr*{8}).
  \item \textbf{Be learnable:} Clinicians with limited technical experience should be able to complete core tasks without training, such as adding a patient, assigning speaker roles, and viewing results (\srsnfr*{1}, \srsnfr*{2}).
  \item \textbf{Support a seamless workflow:} Clinicians should be able to move from selecting a patient to downloading a report without losing work between stages (\srsfr*{5}, \srsnfr*{3}).
  \item \textbf{Make generated content clear:} Clinicians should always be able to tell which content was automatically generated and which they have verified (\srsfr*{14}, \srsnfr*{14}).
  \item \textbf{Be measured through user testing:} Success is measured through usability testing with clinicians, using task completion rate, time on task, and a post-task survey (Appendix).
\end{itemize}

\subsubsection{Out of Scope}
Some objectives are out of scope for this VnV plan due to time and resource limitations:
\begin{itemize}
  \item \textbf{Advanced detection of clinical cues:} Detecting subtle behavioural or linguistic signals beyond interference flags and grammar and phonology suggestions is a stretch goal. It will only be verified if implemented, since validating it would require clinical expertise and labelled data the team does not have.
  \item \textbf{Accuracy of third-party speech services:} The speech recognition and keyword detection services (Whisper and Deepgram) are assumed to have been verified by their developers. The plan verifies that TeLaC handles their output correctly and that clinicians can review and correct it, not the services' accuracy on code-mixed speech.
  \item \textbf{Administrative and physical HIPAA safeguards:} Staff training and breach notification procedures are the responsibility of the institutions that use TeLaC, as stated in SRS Section 7.5. Only the technical safeguards are verified.
  \item \textbf{Full UI standards compliance:} The focus is on practical usability for clinicians rather than exhaustive WCAG compliance or visual polish.
\end{itemize}

\subsection{Custom Documents} \label{sec:CustomDocs}

Two custom documents (CDs) were chosen in the Problem Statement, and both support this VnV plan.
Improving SAFA's usability is one of the project's main goals, and many of the requirements in the \SRSLink{} are about how easily clinicians can use the system (\srssr*{8}, \srsnfr*{1}, \srsnfr*{2}, \srsnfr*{14}).
These are hard to verify with automated tests alone, so the CDs provide the team a structured way to evaluate them with real users.
The Wireframe is used first to validate the requirements and the interface design before finalizing the implementation, and the Usability Report is used later to verify that the system actually meets the usability requirements.

\subsubsection{Wireframe (Fall)}
The Wireframe is a mock-up of SAFA's redesigned interface (although it can also include mockups for the TeLaC application pages), covering the integrated SAFA annotation tool and the main workflow screens (selecting a patient and assessment, choosing a workflow, reviewing and correcting the transcript, and generating a report).
It will be made using a design tool like Figma and presented to the supervisor, the research team, and clinicians.
Its role in this plan is validation rather than verification, as it checks that the requirements describe what clinicians actually need before the interface is implemented.
During the review, the team will:
\begin{itemize}
  \item Present each workflow by walking reviewers through the mock-up and ask whether the steps match how they would normally analyze an assessment (\srssr*{5})
  \item Ask reviewers to point out which content is automatically generated and which they have verified, which can be an early check of \srsnfr*{14}
  \item Get feedback on the overall look and layout of the transcripts, both in the TeLaC view and the SAFA view
  \item Make note of any labels, icons, or steps that reviewers find unclear (\srsnfr*{2})
  \item Record missing features or changes reviewers request
\end{itemize}
The document will describe the mock-ups and discuss the insights gained due to this review.
Any feedback that changes a requirement will be added to the \SRSLink{} and tracked as its own GitHub issue.

\subsubsection{Usability Report (Winter)}
The Usability Report verifies the usability requirements against the final system.
It will contain the testing plan, the results, and a discussion of the findings and user feedback. This includes any suggested improvements to how the system looks and functions.
The testing will be systematic and quantified so that the results can be compared directly against the fit criteria of the usability requirements defined in the \SRSLink{}.
The test plan will include the following (this is subject to change over the course of the project):
\begin{itemize}
  \item \textbf{Participants:} clinicians that will be provided by the research team's contacts who have not been trained on the system
  \item \textbf{Tasks:} core tasks such as adding a patient, assigning a speaker role, correcting a transcript chunk, adding an annotation, and generating a report. These are the same features tested for correctness in Section~\ref{sec:System_Tests} (e.g., FR-ST-TR1 and FR-ST-TR2), so the usability sessions only measure how easily clinicians can use them
  \item \textbf{Measures:} task completion rate, time to complete each task, number of times the participant needed help, and whether each function was found on the first attempt
  \item \textbf{Survey:} a post-test questionnaire on ease of use and satisfaction (Appendix~\ref{sec:UsabilitySurvey})
\end{itemize}
The results will also be compared with the standalone SAFA tool, since the Problem Statement measures the usability goal as an improvement over the current SAFA interface.
The Usability and Understandability tests in Section~\ref{sec:System_Tests} will be run as part of these sessions, and the results will be reported in the VnV Report.

\subsection{SRS Verification} \label{sec:SRSVerification}

The \SRSLink{} is verified through four reviews, each suited to catching a different kind of problem. 
The team first checks its own work for completeness and consistency, the peer review team and TA then check that the document is clear to an outside reader, and finally the supervisor and research team check that it describes what clinicians actually need. 
Feedback from all four reviews is tracked the same way, which is to create a dedicated GitHub issue for each piece of actionable feedback.

\paragraph{Internal Checklist Review:}
Before each SRS revision is submitted, every team member reviews the sections written by another member. This way, each section is looked over by someone other than the original author. 
The reviewer works through the SRS checklist, which covers the template and writing quality, along with the project-specific checklist below. The checklist the team decided on covers problems that are specific to this project. 
These checks are done in the pull request for each section, which already needs approval from at least one other team member before it can be merged (\DevPlanLink). 
The reviewer leaves a comment on any item that fails, and the pull request is not approved until it is fixed or the author explains why no change is needed.

\begin{itemize}[label=\checkbox]
  \item Every functional requirement traces to at least one stakeholder requirement.
  \item Every stakeholder requirement is supported by evidence from the research team's study (\SRSLink{} Appendix A) or by a supervisor decision.
  \item Every functional and non-functional requirement has a fit criterion that a tester could check without asking the author what it means.
  \item Every threshold in a fit criterion is written as a symbolic constant rather than a fixed number.
  \item Every functional and non-functional requirement is covered by at least one system test in Section~\ref{sec:System_Tests}.
  \item Each requirement states what the system must do, not how it will be built.
  \item The use cases, functional requirements, and workflow state diagrams use the same names for the same states and actions.
  \item Each of the three clinician workflows (Direct Analysis, Annotation-First, and On-Demand Refinement) can be traced from start to finish through the use cases without a missing step.
  \item Automatically generated content (transcripts, scores, and flags) is always treated as a suggestion the clinician can review and correct (\srssr*{3}).
  \item Every requirement that involves patient data states who is allowed to access it (\srssr*{7}).
  \item Requirements refer to the supported assessment languages in general, rather than naming a specific language pair.
  \item Domain terms (e.g., code-switching, speaker role, chunk) are defined in the Definitions and Acronyms section before they are used.
\end{itemize}

\paragraph{Peer and TA Review:}
The assigned peer review team and the TA read the SRS without any prior knowledge of the application or speech language domain. 
Since they have no background in speech-language pathology, they are best suited to find sections that are unclear or that assume domain knowledge, which also matters for future developers who will need to maintain the system. 
Peer reviewers report each problem as a GitHub issue using the team's Peer Review issue template, which records the artifact, the reviewing team, and a description of the problem. TA feedback from grading documents is turned into issues in the same way.

\paragraph{Supervisor and Research Team Review:}
The supervisor and research team are the only reviewers who can confirm that the requirements match real clinical practice.
Their review is guided by a requirements feedback form, given in full in Appendix~\ref{sec:ReqFeedbackForm}, which links to the functional requirements. The form only covers what the team will build and leaves out the recording features already built by the previous capstone team. It asks whether the requirements reflect how they would ideally review a remote assessment, what is missing, what should be changed or removed, which requirements are essential in a clinical setting, and which 10--15 requirements should be prioritized for the first demo. It also asks them to make decisions the team cannot make on its own: how the generated transcript should be displayed in the assessment interface (\srssr*{2}), what information a clinical report should be generated from (\srssr*{6}, \srsfr*{7}), who may view or download recordings (\srssr*{7}), and which pattern detection features are in scope.

Since the supervisors are busy and more likely to give feedback during scheduled meetings than on their own time, the form is used as the question guide for breakout sessions during the virtual supervisor meetings, organized using the team's Supervisor Meeting issue template. The form is also shared ahead of time, so supervisors can respond in writing if they prefer. During each session, a team member records the answers in the form, so the team keeps a written record of each supervisor's feedback. When an answer is unclear or supervisors disagree, the team walks through the related workflow step by step using its use cases and state diagram, so that they can point out exactly where it differs from their practice. The sessions also cover what the form cannot, such as whether the values proposed for the symbolic constants are realistic (e.g., the task success rate and task time in \srsnfr*{1} and \srsnfr*{2}). The agreed priority list then decides which requirements are implemented first for the Proof of Concept and Revision 0 demos. Validation with clinicians continues through the Wireframe CD (Section~\ref{sec:CustomDocs}), where clinicians can provide feedback after seeing visual mockups. This might help them point out any changes that need to be made in a way that is easier than reading written requirements.

\paragraph{Feedback Tracking:}
Every requested change, whether from the checklist review, peer review, TA, form, or meeting, becomes a GitHub issue assigned to the owner of the affected section. 
Each issue is closed by a pull request that links to it, or closed with a written reason if the team decides not to make the change. All changes must be recorded in the SRS document's revision history table.
An SRS revision is considered verified once all four reviews are complete and every resulting issue has been closed.

\subsection{Design Verification}

The design of TeLaC will be documented once the design stage begins. 
Afterwards, design documents will be verified through a combination
of internal team reviews, peer and TA reviews, supervisor
reviews, and designated design review sessions with the research
team and clinicians.

\begin{itemize}
  \item \textbf{Internal team review:} Each design document will be reviewed
  by at least one team member who did not write it. The reviewer will also check
  the document against the design checklists provided in the course
  repository, and any problems found will be logged as GitHub issues.
  On completion of an interface, a member of the team will also review it to
  ensure that it follows the Wireframe.
  \item \textbf{Peer and TA review:} The assigned peer review team and the
  course TA will review the design documents. Their feedback will be logged
  as GitHub issues, assigned to a team member, and closed with a reference to
  the commit that resolves it.
  \item \textbf{Supervisor review:} The design will be presented to the
  supervisor during a scheduled meeting. The team will walk through the
  module decomposition and the main data flow, from uploading a recording to
  transcription, SAFA analysis, and report generation, and ask whether the
  design fits the needs of the research team. If changes are needed, they will
  be noted and the design documents will be updated before implementation.
  \item \textbf{Stakeholder review:} When presenting the Wireframe of the redesigned
  interface to our stakeholders (clinicians and researchers), a short questionnaire on 
  layout, navigation, and workflow will be provided for them to fill out. 
  Their responses will be used to revise the interface before implementation. 
  The questionnaire will be included in the appendix of this document and 
  expanded on in the Usability Report.
\end{itemize}

During these reviews, the team will also confirm that:

\begin{itemize}
  \item Every functional requirement in the \SRSLink{} is assigned to at least
  one module in the design.
  \item Each module hides a single design decision that is likely to change,
  such as the speech recognition model or the database.
  \item Module interfaces are consistent with each other,
  and each one has clearly defined inputs, outputs, and exceptions.

\subsection{Implementation Verification}

The implementation will be verified through the system tests in Section~\ref{sec:System_Tests} and the unit tests in Section~\ref{sec:UnitTests}, and statically through the automated tools in Section~\ref{sec:AutoTools}. 
This section covers the manual checks that those tools cannot perform and that the team must do.

Every pull request is inspected by at least one other team member before it is merged (\DevPlanLink). 
In addition to the general items in the pull request template, the reviewer checks that each endpoint verifies the clinician is allowed to access the requested patient (\srssr*{7}), that no patient data is written to logs, and that failures from external services such as the transcription model or storage are handled without losing the clinician's work. The system tests (e.g., NFR-ST-RE2 and NFR-ST-CV3) check that work is kept under normal conditions, but not when an external service fails.

Finally, after the Revision 0 demo, the team will lead a code walkthrough with Dr.\ Yue, one of the project's supervisors and a software engineering professor at California State University San Marcos.
The walkthrough will focus on the modules from the \HALink{} that handle patient data and transcripts, which are the account system, the database, and the transcription pipeline. During the walkthrough, the team will also look for race conditions, data handling problems, and security issues. Race conditions in particular are not covered by the system tests: for example, NFR-ST-CV2 only checks edits made on one device at a time, not two sessions saving edits to the same transcript chunk at once. 
The team will send him the relevant code by sharing a link to the GitHub repository, as well as a short list of questions beforehand. Each finding from the code walkthrough is to be recorded as a GitHub issue. 
Where possible, each issue is closed together with a new test that reproduces the problem, so that the fixes are documented and visible in case it ever happens again.

  \item Linters: Ruff (Python), ESLint (TypeScript/JavaScript)
  \item Continuous Integration: GitHub Actions

The CI workflows and tooling are described further in the described further in the \DevPlanLink.

For code coverage, Coverage.py is used for the Python code. For TypeScript/JavaScript, Istanbul is used. 
This is considering it is built into Jest, which reduces the number of additional frameworks needed. 
Both tools report which lines and functions are not covered by the tests, so the team can see where additional tests are needed. 
The team’s target is approximately 80\% for line coverage, considering that is the current standard. 
Furthermore, it keeps the testing effort balanced with the time available for developing the software.

Ruff is used to ensure the Python coding standard (PEP 8) is respected. 
It was chosen for its speed compared to alternative linters. 
Additionally, since TypeScript/JavaScript makes up a large part of the codebase, ESLint is used to find and report problematic patterns and bugs in that code. 
ESLint is the industry standard for static analysis of JavaScript, which is why it was chosen. 
Moreover, GitHub Actions runs the unit tests and the linting checks on every pull request that is opened or updated and on every merge to main. 
A pull request with failing checks must be fixed before it can be merged.

\subsubsection{Transcript Review and Editing} \label{sec:TranscriptTests}
This section verifies that clinicians can correct the automatically generated transcript, assign a role to each speaker, filter the transcript by role, and choose which parts of an assessment to open in the SAFA tool.
All tests in this section and in the Playback and Navigation, Performance, and Convenience sections use test recordings, since real patient data is not to be used during development.
Test assessment A is an approximately 5-minute recording involving two speakers (child and parent), speech in more than one supported language (English and Mandarin), 10 questions, and about 15 transcript segments.
Test assessment B is a recording of the maximum length allowed by the system (MAX\_REC\_LEN minutes) that will be used for timing tests.
For each assessment, the stored transcript (each segment's start and end time, speaker, and the time each question was asked) is recorded before testing and serves as the answer key.
\begin{enumerate}
  \item FR-ST-TR1: \textbf{Edit and Save Transcript Text\\}
  \begin{mdframed}[linewidth=0.5mm]
      \textbf{Purpose:} Verifies that a clinician can add, delete, and modify transcript text. Also verifies that saved changes persist, and that unsaved changes can be discarded.\par
      \textbf{Type:} Manual, Dynamic \par
      \textbf{Initial State:} A clinician account is logged in, and test assessment A is open in the SAFA tool with its auto-generated transcript, with no segments edited. \par
      \textbf{Input:} 5 segments of test assessment A, documented before testing with their original text. In segment 1 a word is added, in segment 2 a word is deleted, and in segment 3 a word is replaced and its language tag is changed. Segment 4 is edited and then discarded, and segment 5 is edited and left unsaved. \par
      \textbf{Output:} Segments 1--3 show the edited text after saving, their original auto-generated text is kept and the differences are shown, and each is marked as verified with who made the change and when. Segment 4 returns to its original text. Trying to leave the transcript with segment 5 unsaved prompts the clinician to save or discard. After closing and reopening the assessment, segments 1--3 still show the edited text. \par
      \textbf{Test Case Derivation:} \srsfr*{2} requires that clinicians can add, delete, and modify transcript text and that saved changes persist when the recording is reopened. \srsuc*{9} adds that the original version is kept, the segment is marked as verified, and unsaved changes can be discarded or prompt the user before leaving. Clinicians rely on these corrections being kept, since all later annotations and analysis are based on the corrected text. \par
      \textbf{How the test will be performed:}
      \begin{enumerate}
        \item[1.] Make the listed edits to segments 1--3 and save each one.
        \item[2.] Check that each edited segment shows the new text, the original text, the differences, and its verified status with the editor and time.
        \item[3.] Edit segment 4, discard the change, and check that it shows its original text.
        \item[4.] Edit segment 5 without saving, try to leave the transcript, and check that the system asks whether to save or discard. Discard the change.
        \item[5.] Close the assessment, reopen it, and check that segments 1--3 still show the edited text.
      \end{enumerate}
  \end{mdframed}

  \item FR-ST-TR2: \textbf{Assign a Role to Each Detected Speaker\\}
  \begin{mdframed}[linewidth=0.5mm]
      \textbf{Purpose:} Verifies that once a clinician assigns a role to a speaker the system detected, every segment from that speaker is labeled with the role. \par
      \textbf{Type:} Manual, Dynamic \par
      \textbf{Initial State:} A clinician account is logged in, and test assessment A is open in the SAFA tool with its auto-generated transcript and two detected speakers, neither of which have a role. \par
      \textbf{Input:} The roles Child and Parent are each assigned once to the matching detected speaker. One of the segments contains both speakers. \par
      \textbf{Output:} Every segment from each speaker shows that speaker's role, and the number of segments labeled with each role matches the answer key. In the segment with both speakers, each speaker's part is labeled with their own role. The roles are still shown after the assessment is closed and reopened. \par
      \textbf{Test Case Derivation:} \srsfr*{6} requires that every segment from a detected speaker is labeled with the role the clinician assigns, and \srsuc*{5} requires that each speaker in a segment with more than one speaker is labeled separately. Clinicians need the child's speech separated from the adults' to analyze the child's language and to find parent interference. \par
      \textbf{How the test will be performed:}
      \begin{enumerate}
        \item[1.] Select a segment from the first speaker and assign the role Child.
        \item[2.] Repeat step 1 for the role Parent.
        \item[3.] Count the segments labeled with each role and compare the counts to the answer key.
        \item[4.] Check that each speaker in the segment with both speakers is labeled with their own role.
        \item[5.] Close and reopen the assessment, and check that all roles are still shown.
      \end{enumerate}
  \end{mdframed}

  \item FR-ST-TR3: \textbf{Filter the Transcript by Speaker Role\\}
  \begin{mdframed}[linewidth=0.5mm]
      \textbf{Purpose:} Verifies that filtering the transcript by a speaker role shows exactly that speaker's segments. \par
      \textbf{Type:} Manual, Dynamic \par
      \textbf{Initial State:} A clinician account is logged in, and test assessment A is open in the SAFA tool with the roles from FR-ST-TR2 assigned. \par
      \textbf{Input:} The filters Child, then Parent, then no filter. \par
      \textbf{Output:} For Child and Parent, exactly the segments the answer key lists for that role are shown, and no others. The segment containing both speakers is shown under both filters. With no filter, all segments are shown again in their original order. \par
      \textbf{Test Case Derivation:} \srsfr*{6} requires that clinicians can filter the transcript by speaker role. Clinicians use this to review only the child's answers, or only the parent's speech when checking for interference, so a filter that hides or adds segments would lead to an incomplete analysis. \par
      \textbf{How the test will be performed:}
      \begin{enumerate}
        \item[1.] Filter by Child and compare the segments shown to the answer key's Child segments.
        \item[2.] Repeat step 1 for Parent.
        \item[3.] Remove the filter and check that all segments are shown in their original order.
      \end{enumerate}
  \end{mdframed}

  \item FR-ST-TR4: \textbf{Open Selected Questions in the SAFA Tool\\}
  \begin{mdframed}[linewidth=0.5mm]
      \textbf{Purpose:} Verifies that a clinician can choose which questions, or the full assessment, to open in the SAFA tool, and that only those portions are opened. \par
      \textbf{Type:} Manual, Dynamic \par
      \textbf{Initial State:} A clinician account is logged in, and the assessment overview of test assessment A is open. \par
      \textbf{Input:} Questions 3 and 7 are selected and opened in the SAFA tool. Then the full assessment is selected and opened. \par
      \textbf{Output:} When questions 3 and 7 are opened, the SAFA tool shows only the segments and the portions of the recording for those 2 questions, and playback does not continue into other questions. When the full assessment is opened, all segments and the full recording are shown. \par
      \textbf{Test Case Derivation:} \srsfr*{15} requires that the clinician can select one or more questions, or the full assessment, and that only those portions are opened in the SAFA tool. This supports the On-Demand Refinement workflow, where clinicians only annotate flagged or unclear questions to save time. \par
      \textbf{How the test will be performed:}
      \begin{enumerate}
        \item[1.] From the overview, select questions 3 and 7 and open them in the SAFA tool.
        \item[2.] Compare the segments shown with the answer key's segments for questions 3 and 7.
        \item[3.] Play the recording to the end of question 3 and check that playback does not continue into question 4.
        \item[4.] Return to the overview, select the full assessment, open it, and check that all segments are shown.
      \end{enumerate}
  \end{mdframed}
\end{enumerate}

\subsubsection{Playback and Navigation}
This section verifies that the transcript and recording stay linked, so that clinicians can follow along during playback and jump to any segment or question, and that clinicians can move between workflow stages without losing saved work.
The timing tolerances for these features are tested separately in the Performance section.
\begin{enumerate}
  \item FR-ST-PN1: \textbf{Highlight the Current Segment During Playback\\}
  \begin{mdframed}[linewidth=0.5mm]
      \textbf{Purpose:} Verifies that during playback the system highlights the segment being spoken and scrolls the transcript so that it is visible. \par
      \textbf{Type:} Manual, Dynamic \par
      \textbf{Initial State:} A clinician account is logged in, and test assessment A is open in the SAFA tool with playback at the start of the recording. \par
      \textbf{Input:} 10 playback times chosen from the answer key, spread across the recording. One is in a segment that is off-screen when playback starts, and one is reached by dragging the playback bar instead of playing. \par
      \textbf{Output:} At each of the 10 times, the highlighted segment is the one whose start and end times contain the playback position, and it is visible in the transcript without the clinician scrolling. \par
      \textbf{Test Case Derivation:} \srsfr*{20} requires that the highlighted segment is the one whose start and end times contain the playback position, and that the transcript scrolls to keep it visible. \srsuc*{8} describes clinicians following the transcript while watching the recording, which only works if the highlight is on the right segment. \par
      \textbf{How the test will be performed:}
      \begin{enumerate}
        \item[1.] Play the recording and pause at the first listed time.
        \item[2.] Check that the highlighted segment's start and end times, from the answer key, contain the playback position, and that the segment is visible.
        \item[3.] Repeat steps 1--2 for the remaining times. For the time listed as reached by dragging, drag the playback bar to it instead of playing.
      \end{enumerate}
  \end{mdframed}

  \item FR-ST-PN2: \textbf{Jump to a Selected Segment\\}
  \begin{mdframed}[linewidth=0.5mm]
      \textbf{Purpose:} Verifies that selecting a transcript segment moves playback to the start of that segment and highlights it. \par
      \textbf{Type:} Manual, Dynamic \par
      \textbf{Initial State:} A clinician account is logged in, and test assessment A is open in the SAFA tool. \par
      \textbf{Input:} 5 segments: the first, the last, one in the middle, one that is off-screen, and one shorter than 1 second. Each is selected once while playback is paused and once while it is playing (10 selections in total). \par
      \textbf{Output:} After each selection, the playback position is at the segment's start time from the answer key, and that segment is highlighted. \par
      \textbf{Test Case Derivation:} \srsfr*{21} requires that selecting a segment sets the playback position to its start time and highlights it. Clinicians use this to re-watch a child's answer or a flagged moment, and the first, last, and very short segments are the ones most likely to be handled wrongly. \par
      \textbf{How the test will be performed:}
      \begin{enumerate}
        \item[1.] With playback paused, select the first listed segment.
        \item[2.] Check that the playback position matches the segment's start time and the segment is highlighted.
        \item[3.] Repeat steps 1--2 for the remaining segments.
        \item[4.] Repeat steps 1--3 while the recording is playing.
      \end{enumerate}
  \end{mdframed}

  \item FR-ST-PN3: \textbf{Jump to a Selected Question or Moment\\}
  \begin{mdframed}[linewidth=0.5mm]
      \textbf{Purpose:} Verifies that selecting a question or a flagged moment starts playback at the point in the recording where it occurred. \par
      \textbf{Type:} Manual, Dynamic \par
      \textbf{Initial State:} A clinician account is logged in, and test assessment A is open in the Individual Assessment View with at least one flagged moment. \par
      \textbf{Input:} 5 questions selected from the question list, including the first and last question, and 1 flagged moment. \par
      \textbf{Output:} After each selection, playback starts at the time the answer key lists for when that question was asked or that moment occurred. \par
      \textbf{Test Case Derivation:} \srsfr*{14} requires that selecting a question or a specific moment starts playback at that point in the assessment. This saves clinicians from searching through the whole recording to find a question. \par
      \textbf{How the test will be performed:}
      \begin{enumerate}
        \item[1.] Select the first listed question.
        \item[2.] Check that playback starts at the time listed in the answer key for that question.
        \item[3.] Repeat steps 1--2 for the remaining questions and the flagged moment.
      \end{enumerate}
  \end{mdframed}

  \item FR-ST-PN4: \textbf{Move Between Workflow Stages Without Losing Saved Work\\}
  \begin{mdframed}[linewidth=0.5mm]
      \textbf{Purpose:} Verifies that clinicians can move forward and back between all workflow stages without losing saved work, and that the system shows the current and completed stages. \par
      \textbf{Type:} Manual, Dynamic \par
      \textbf{Initial State:} A clinician account is logged in, and test assessment A is open in the assessment overview, with no saved work. \par
      \textbf{Input:} The clinician moves from the overview to the SAFA tool and saves 2 transcript edits, then to the evaluation stage and saves a grade for 1 question, then to the report stage. The clinician then goes back to each earlier stage in reverse order. \par
      \textbf{Output:} At every stage, both edits and the grade are still shown. The progress indicator always shows the current stage and marks each stage already visited as completed. \par
      \textbf{Test Case Derivation:} \srsfr*{5} requires that clinicians can move between all workflow stages without losing saved work, and that the system shows the current and completed stages. Clinicians do not analyze an assessment in a straight line, and often go back to correct earlier work. \par
      \textbf{How the test will be performed:}
      \begin{enumerate}
        \item[1.] Move through the stages in order, saving the listed edits and grade, and check the progress indicator at each stage.
        \item[2.] Go back to each earlier stage in reverse order.
        \item[3.] At each stage, check that both edits and the grade are shown and the progress indicator is correct.
      \end{enumerate}
  \end{mdframed}
\end{enumerate}

      \item[1.] Set the camera and microphone as described for Attempt 1, try to start the assessment, and record whether it proceeds and the reason shown if it does not.
      \item[2.] Repeat step 1 for Attempts 2 and 3.
      \item[3.] Check that Attempts 1 and 2 are blocked with the correct reason, and that Attempt 3 proceeds.
      \end{enumerate}
  \end{mdframed}
\end{enumerate}

\begin{enumerate}

      \textbf{Input:} One mock video assessment conducted on the system, with one edit made to one of its annotations and saved. \par
      \textbf{Output:} After one BACKUP\_INTERVAL, a backup for the mock assessment recording exists, including the edited annotation for the assessment transcript. \par
      \textbf{How the test will be performed:}
      \begin{enumerate}
      \item[1.] Conduct the mock video assessment on the system.
      \item[2.] Edit one annotation, save it, and note the time.
      \item[3.] Wait one BACKUP\_INTERVAL.
      \item[4.] Open the backup storage and check that a backup exists and contains the recording and the edited annotation.

  \item NFR-ST-M2: \textbf{Restore from Backup\\}
  \begin{mdframed}[linewidth=0.5mm]

      \textbf{Type:} Nonfunctional, Dynamic, Manual \par
      \textbf{Initial State:} The system is running with a test clinician account for each participant, and each account has 1 test patient with 1 completed assessment. The participants have not used the system before and receive no training. \par

      \item[2.] Delete the mock assessment from the system.
      \item[3.] Restore the system from the backup.

\subsubsection{Security}
This section verifies that patient data is protected. Clinicians can only access their own patients, idle sessions time out, data is encrypted in transit and in storage, and all access to patient data is logged.
\begin{enumerate}
  \item NFR-ST-S1: \textbf{Restrict Access to Assigned Patients\\}
  \begin{mdframed}[linewidth=0.5mm]
      \textbf{Purpose:} Verifies that a clinician cannot access another clinician's patients through the interface, by URL, or through the API. \par
      \textbf{Type:} Nonfunctional, Dynamic, Automatic \par
      \textbf{Initial State:} The test database contains two clinicians, each with 2 assigned patients that have at least one assessment. The patient and assessment IDs are documented prior to testing for later reference. \par
      \textbf{Input:} While logged in as the first clinician, 3 requests for each of the second clinician's patients: opening the patient's page by URL, requesting the patient record through the API, and requesting one of the patient's recordings through the API. \par
      \textbf{Output:} All requests are denied with an access error, and no patient data, transcripts, or recordings belonging to the second clinician are returned (\srsnfr*{5}). \par
      \textbf{How the test will be performed:}
      \begin{enumerate}
      \item[1.] Using an automated test, load the data from the test database and log in as the first clinician.
      \item[2.] Send each request in the input list using the second clinician's documented IDs.
      \item[3.] Check that every request returns an access error and that no response contains the second clinician's patient data.
      \end{enumerate}
  \end{mdframed}

  \item NFR-ST-S2: \textbf{Session Timeout After Inactivity\\}
  \begin{mdframed}[linewidth=0.5mm]
      \textbf{Purpose:} Verifies that an idle session expires, the clinician's work is saved, and the clinician must log in again before any patient data is shown. \par
      \textbf{Type:} Nonfunctional, Dynamic, Manual \par
      \textbf{Initial State:} A clinician account is logged in, and an assessment is open with one unsaved transcript edit. \par
      \textbf{Input:} No activity in the browser for IDLE\_TIMEOUT minutes, then an attempt to open another patient record. \par
      \textbf{Output:} After IDLE\_TIMEOUT minutes, the system saves the clinician's work, returns them to the login page with a message explaining the session ended due to inactivity, and shows no patient data until they log in again (\srsnfr*{6}). \par
      \textbf{How the test will be performed:}
      \begin{enumerate}
      \item[1.] Make one transcript edit without saving, and note the time.
      \item[2.] Leave the browser idle for IDLE\_TIMEOUT minutes, then check that the login page is shown with the inactivity message.
      \item[3.] Try to open another patient record and press the browser's back button, and check that no patient data is shown in either case.
      \item[4.] Log back in, reopen the assessment, and check that the transcript edit was saved.
      \end{enumerate}
  \end{mdframed}

  \item NFR-ST-S3: \textbf{Encrypt Data in Transit\\}
  \begin{mdframed}[linewidth=0.5mm]
      \textbf{Purpose:} Verifies that recordings, transcripts, and patient data are encrypted using TRANSIT\_ENCRYPTION\_STANDARD when sent between the browser and the server, and from the server to third-party transcription services. \par
      \textbf{Type:} Nonfunctional, Dynamic, Manual \par
      \textbf{Initial State:} A clinician account is logged in, and a network capture tool is running on the test device. \par
      \textbf{Input:} 5 actions performed while traffic is captured: logging in, opening a patient record, playing a recording, downloading a report, and submitting a recording for transcription. \par
      \textbf{Output:} All captured traffic uses and requests to the transcription service use TRANSIT\_ENCRYPTION\_STANDARD, and no patient data, credentials, or recordings appear in plain text (\srsnfr*{7}). \par
      \textbf{How the test will be performed:}
      \begin{enumerate}
      \item[1.] Start the capture and perform each action in the input list.
      \item[2.] Stop the capture and check the protocol and version used by each connection.
      \item[3.] Search the capture for the patient's name and the clinician's email, and check that neither appears in plain text.
      \item[4.] Try to open the site over unencrypted HTTP and check that the connection is redirected to an encrypted one or refused.
      \item[5.] Check the server logs for the transcription request and confirm it was sent using TRANSIT\_ENCRYPTION\_STANDARD.
      \end{enumerate}
  \end{mdframed}

  \item NFR-ST-S4: \textbf{Encrypt Stored Data\\}
  \begin{mdframed}[linewidth=0.5mm]
      \textbf{Purpose:} Verifies that stored recordings and transcripts are encrypted using STORAGE\_ENCRYPTION\_STANDARD. \par
      \textbf{Type:} Nonfunctional, Static and Dynamic, Manual \par
      \textbf{Initial State:} One mock assessment with a recording and transcript has been saved to the system. \par
      \textbf{Input:} The database and file storage configuration, and the raw stored files for the mock assessment. \par
      \textbf{Output:} The storage configuration shows 
      \\STORAGE\_ENCRYPTION\_STANDARD is enabled for the 
      \\database and file storage, and the raw stored recording and transcript cannot be read outside the system (\srsnfr*{7}). \par
      \textbf{How the test will be performed:}
      \begin{enumerate}
      \item[1.] Review the storage configuration and record the encryption setting for each storage location.
      \item[2.] Access the raw stored files for the mock assessment directly, outside the system.
      \item[3.] Check that the recording cannot be played and the transcript text cannot be read.
      \end{enumerate}
  \end{mdframed}

  \item NFR-ST-S5: \textbf{Log Access to Patient Data\\}
  \begin{mdframed}[linewidth=0.5mm]
      \textbf{Purpose:} Verifies that every access to patient data is recorded in an audit log that clinicians cannot edit. \par
      \textbf{Type:} Nonfunctional, Static and Dynamic, Automatic and Manual \par
      \textbf{Initial State:} A clinician account is logged in, and a patient record with one assessment exists. \par
      \textbf{Input:} 4 actions on the patient's assessment: viewing it, editing one transcript segment, downloading the
       recording, and exporting the report. The time of each action is documented for later reference. \par
      \textbf{Output:} The audit log contains one entry for each action, with the user, the action, the item affected, and the date and time. 
      Attempts by the clinician to edit or delete entries are denied (\srsnfr*{8}). \par
      \textbf{How the test will be performed:}
      \begin{enumerate}
      \item[1.] Using an automated test, perform each action in the input list as the clinician.
      \item[2.] Check that the audit log has a matching entry for each action, with the correct user, action, item, and time.
      \item[3.] While logged in as the clinician, try to edit and delete a log entry through the interface and the API, and check that both are denied.
      \end{enumerate}
  \end{mdframed}
\end{enumerate}

\subsection{Usability Survey Questions} \label{sec:UsabilitySurvey}

The following survey will be given to each participant right after their usability testing session in the Usability Report CD (Section~\ref{sec:CustomDocs}).
Since the system has not been built yet, this section is a work in progress and will be finalized after the Wireframe review to account for any changes the team might make in response to clinician feedback.
Participants will be asked to complete the same survey after doing the same tasks in the original standalone SAFA tool, so the two scores can be compared.

\paragraph{Part A: System Usability Scale}
Part A uses the System Usability Scale (SUS) \citep{Brooke_SUS_1996}, a standard ten-item questionnaire that produces a single usability score from 0 to 100.
This scale was chosen because it is short, widely used, and gives a score that can be compared between the integrated system and the standalone SAFA tool.
Each statement is rated from 1 (strongly disagree) to 5 (strongly agree).

\begin{enumerate}
  \item I think that I would like to use this system frequently.
  \item I found the system unnecessarily complex.
  \item I thought the system was easy to use.
  \item I think that I would need the support of a technical person to be able to use this system.
  \item I found the various functions in this system were well integrated.
  \item I thought there was too much inconsistency in this system.
  \item I would imagine that most people would learn to use this system very quickly.
  \item I found the system very cumbersome to use.
  \item I felt very confident using the system.
  \item I needed to learn a lot of things before I could get going with this system.
\end{enumerate}

\paragraph{Part B: Project-Specific Questions}
The SUS measures overall ease of use, but does not cover the specific usability requirements that the team defined in the \SRSLink{}.
This part adds statements that target those requirements, rated on the same 1 to 5 scale.
These ratings show how participants felt about each requirement, while the task results recorded by the team during the session (completion rate, time, and help needed) are used to check whether the fit criteria are met.

\begin{enumerate}[resume]
  \item I could find each function I needed on my first attempt by reading the labels on the screen (\srsnfr*{2}).
  \item I could always tell which transcript content and results were automatically generated and which I had verified (\srsnfr*{14}).
  \item I could easily return to an earlier stage without losing my work (\srsnfr*{3}).
  \item After I made a change, it was clear that the system had saved it (\srsnfr*{4}).
  \item Following the transcript alongside the video playback was easy (\srsfr*{20}).
  \item Reviewing, annotating, and reporting on an assessment in one place would save me time compared to my current process (\srssr*{1}, \srssr*{2}).
\end{enumerate}

\paragraph{Part C: Open-Ended Questions}
\begin{enumerate}[resume]
  \item Which task was the most difficult to complete, and why?
  \item Was anything on the web pages confusing or unclear?
  \item What would you change or add to make the system fit better into your daily workflow or help streamline your tasks?
  \item Is there anything else you would like to tell us about your experience?
